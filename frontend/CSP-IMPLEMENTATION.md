# Content Security Policy (CSP) Implementation

## Overview

This application implements a **strict, nonce-based Content Security Policy** to provide robust protection against Cross-Site Scripting (XSS) attacks and other injection vulnerabilities.

## What Changed

### Before (Allowlist-based CSP)
- Used `'unsafe-inline'` and `'unsafe-eval'` directives
- Allowed all inline scripts and styles
- More vulnerable to XSS attacks
- Overly permissive image sources (`https:` allowed all HTTPS images)

### After (Nonce-based Strict CSP)
- Generates unique nonces (cryptographic tokens) for each request
- Only scripts/styles with the correct nonce can execute
- Uses `'strict-dynamic'` for better third-party script handling
- More restrictive and secure

## Implementation Details

### 1. Middleware (`src/middleware.ts`)

The middleware:
- Generates a unique nonce for each request using `crypto.randomUUID()`
- Sets the nonce in the request headers (`x-nonce`)
- Applies the CSP header with the nonce to all responses
- Includes other security headers (HSTS, X-Frame-Options, etc.)

### 2. Root Layout (`src/app/layout.tsx`)

The layout:
- Retrieves the nonce from request headers
- Passes the nonce to inline `<script>` tags
- Passes the nonce to Next.js `<Script>` components

### 3. Configuration (`next.config.ts`)

Removed the static CSP headers since they're now dynamically generated by middleware.

## Security Benefits

1. **XSS Protection**: Only scripts with valid nonces can execute
2. **Unique per Request**: Each page load gets a fresh nonce
3. **No Inline Attacks**: Attackers can't inject inline scripts
4. **Third-party Control**: Explicit allowlist of trusted domains
5. **Future-proof**: `'strict-dynamic'` automatically trusts scripts loaded by trusted scripts

## CSP Directives Explained

```
default-src 'self'                    → Only load resources from same origin by default
script-src 'self' 'nonce-xxx' ...     → Scripts need nonce or be from trusted domains
style-src 'self' 'nonce-xxx' ...      → Styles need nonce (unsafe-inline for compatibility)
img-src 'self' data: https://...      → Images from specific trusted sources
font-src 'self' data: ...             → Fonts from self and Google Fonts
connect-src 'self' https://...        → API calls to specific domains
frame-src https://...                 → Iframes only from trusted sources
object-src 'none'                     → No plugins (Flash, etc.)
base-uri 'self'                       → Prevent base tag injection
form-action 'self'                    → Forms can only submit to same origin
frame-ancestors 'none'                → Prevent clickjacking
upgrade-insecure-requests             → Auto-upgrade HTTP to HTTPS
```

### Manual Testing

#### Check CSP in Browser
1. Open Developer Tools (F12)
2. Go to Network tab
3. Reload the page
4. Click on any HTML document
5. Look for `Content-Security-Policy` in response headers

#### Check for CSP Violations
1. Open Developer Tools (F12)
2. Go to Console tab
3. Look for CSP violation warnings (none = good!)
4. Any blocked resources will appear as errors

## Troubleshooting

### Issue: Scripts are blocked
**Solution**: Add the domain to `script-src` in `src/middleware.ts`

### Issue: Images not loading
**Solution**: Add the domain to `img-src` in `src/middleware.ts`

### Issue: API calls failing
**Solution**: Add the domain to `connect-src` in `src/middleware.ts`

### Issue: Inline styles not working
**Solution**: `'unsafe-inline'` is kept in `style-src` for React inline styles. If you want stricter, you'll need to use CSS modules/Tailwind only.

## Adding New Third-party Scripts

If you need to add a new third-party script:

1. Add the domain to `script-src` in `src/middleware.ts`
2. If it loads resources (images, fonts, etc.), add those domains too
3. If it uses iframes, add to `frame-src`
4. Test thoroughly in dev and staging before production

## Migration Notes

- **Breaking Change**: Any inline scripts without nonces will be blocked
- **Compatibility**: Some older browsers don't support `'strict-dynamic'`
- **Third-party**: Some widgets may need their domains added to CSP

## Performance Impact

- **Minimal**: Nonce generation is very fast (cryptographic UUID)
- **No caching issues**: Nonces are per-request, not per-response
- **CDN compatible**: Works with most CDNs that support custom headers
